# Implementation Guide: Roomba i7 TLS Root Certificate Bypass via NTP Spoofing

## 1. Objective
Force an 8-year-old iRobot Roomba i7 to perform an Over-The-Air (OTA) firmware update by bypassing a likely expired embedded TLS Root CA certificate. This requires intercepting its network time requests (NTP) and serving a spoofed past date to temporarily validate the certificate chain.

## 2. Context & Problem Statement
*   **Device:** iRobot Roomba i7 (MAC Address: `50:14:79:07:BE:71`).
*   **Current State:** Connects to the 2.4GHz IoT Wi-Fi network, successfully obtains an IP address (e.g., `192.168.1.74`), and exchanges initial DNS/NTP packets. However, it immediately drops offline and fails to establish an MQTT over TLS connection (TCP port 8883) to the AWS IoT Cloud (`*.iot.*.amazonaws.com` / `*.irobot.com`).
*   **Root Cause Analysis:** The device firmware relies on hardcoded Root CA certificates. Given the age of the device and the current date (October 2026), one of the critical Root CAs (e.g., DST Root CA X3 or an older Amazon/Symantec root) has expired. The device performs strict certificate pinning and time validation. When it fetches the current date via NTP, it realizes the server's certificate is "expired" according to its local trust store, rejects the TLS handshake, and terminates the connection.
*   **Resolution Strategy:** Use "Time-Travel" spoofing. By intercepting the Roomba's NTP requests and feeding it a date from before the certificate expiration (e.g., January 2023), the Roomba will evaluate the TLS certificate as valid, establish the secure tunnel, and seamlessly download the latest firmware containing the updated Root CAs.

## 3. Environment & Constraints
*   **Main Gateway:** Neufbox (ISP Router). **Constraint:** It acts as the primary DHCP and DNS relay but lacks advanced firewall capabilities, NAT reflection, or granular per-client DNS assignment. However, it **does** support static IP assignment via MAC address.
*   **Access Point:** TP-Link EAP110-Outdoor (SSID: `EAP110-Outdoor-AP`). Operates in bridge mode, broadcasting the 2.4GHz network (20MHz channel width, WPA2-AES).
*   **Available Compute:** Raspberry Pi 5 (running Linux). Can be utilized to host temporary network services and execute interception routing.

## 4. Execution Plan for the Agent

You are tasked with deploying the following interception infrastructure on the Raspberry Pi:

### Step 1: Deploy a Spoofed NTP Server
1. Install and configure a local NTP daemon (e.g., `chrony` or a custom Python UDP script on port 123) on the Raspberry Pi.
2. Hardcode the daemon to serve a static datetime: **January 15, 2023, 12:00:00 UTC**.
3. Ensure it responds to any incoming UDP 123 requests without requiring upstream synchronization.

### Step 2: Implement DNS Interception (Sinkhole)
1. Deploy a DNS forwarder (e.g., `dnsmasq`, Pi-hole, or AdGuard Home) on the Raspberry Pi.
2. Configure DNS rewrite rules to intercept standard pool domains requested by IoT devices and redirect them to the Raspberry Pi's local IP address. 
   *Target Domains to spoof:*
   * `*.pool.ntp.org` (e.g., `0.irobot.pool.ntp.org`, `1.pool.ntp.org`)
   * `time.nist.gov`
   * `time.windows.com`
   * `time.google.com`

### Step 3: Traffic Routing & Network Configuration
Since the Neufbox provides DHCP and cannot push a custom DNS specifically to the Roomba, but allows static IP assignment via MAC address, use a targeted ARP spoofing approach:

1. **Lock the IP:** In the Neufbox DHCP interface, assign a static lease to the Roomba's MAC address (`50:14:79:07:BE:71`) to ensure it consistently operates on a known IP (e.g., `192.168.1.74`). Reboot the Roomba (hold CLEAN for 20s) to force it to acquire this static lease.
2. **Targeted ARP Spoofing:** Execute an ARP spoofing attack (using a tool like `arpspoof` or `ettercap`) targeting exclusively the Roomba's static IP and the Neufbox's IP. This positions the Raspberry Pi as the Man-in-the-Middle (Gateway) only for the vacuum, leaving the rest of the network untouched.
3. **Traffic Redirection (iptables):** Configure IP forwarding on the Raspberry Pi. Use `iptables` to forward standard outbound traffic (TCP 8883/443) to the actual Neufbox so the cloud connection succeeds, but create PREROUTING NAT rules to hijack UDP port 123 to the local spoofed NTP daemon, and UDP port 53 to the local DNS sinkhole.

### Step 4: Monitoring and Validation
1. Run `tcpdump` or `tshark` on the Raspberry Pi to monitor traffic from the Roomba's IP/MAC.
   * `tcpdump -i eth0 host 192.168.1.74 and port 123`
   * `tcpdump -i eth0 host 192.168.1.74 and port 53`
2. Validate that the Roomba requests a time server, receives the spoofed IP via DNS, and accepts the 2023 timestamp via NTP.
3. Monitor TCP port 8883 to confirm a sustained TLS connection is established, indicating the certificate bypass was successful.
4. Wait for the Roomba to complete its OTA firmware download (the status ring may pulse white or the device may reboot).

### Step 5: Teardown
Once the Roomba is visible in the iRobot mobile app and successfully updated:
1. Dismantle the ARP spoofing and flush `iptables` NAT rules.
2. Shut down the spoofed NTP and DNS services on the Raspberry Pi.
3. Reboot the Roomba (hold CLEAN for 20 seconds) to ensure it syncs the correct current time via the standard gateway.
